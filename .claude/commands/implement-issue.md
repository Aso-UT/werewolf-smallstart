---
description: issue番号を受け取り、関連issue・コードを読んで方針を提示し、合意後にPR作成まで実装を進める
argument-hint: <issue番号>
---

issue #$ARGUMENTS を実装する。方針をユーザーと合意したら、PR作成まで止まらずに進める。以下の手順を順番に実行すること。

引数が空、または数字でない場合は、どのissueを実装するかユーザーに確認して終了する。

## 1. issueと関連情報を読む

- `gh issue view $ARGUMENTS --comments` で本文とコメントをすべて読む。
  - 条件の変更はコメントで記録されている。本文だけで判断せず、コメントでの変更を反映した最新の条件を把握する。
- 本文やコメントで参照されているissue・PR（`#番号`）も `gh issue view` / `gh pr view` で読む。
  - 「設計・方針決定」のissueで決まった内容や、前提になっているissueがあれば、その結論を押さえる。
- issueに関わるコードを読む。
  - 変更対象になりそうなクラスだけでなく、呼び出し元・テスト・似たパターンの既存実装も確認する。
  - 既存の命名・設計の流儀（パッケージの依存方向、metadataの扱い、テストの書き方など）に合わせるため、近い機能の実装を参考にする。
- `git status` で作業ツリーに未コミット・未追跡の変更がないか確認する。
  - 変更があっても、勝手にstash・破棄・コミットしない。手順2の提示の中でどう扱うかを確認する。

## 2. 方針をまとめて提示する

以下を整理してユーザーに提示する。

- issueの要件の要約（コメントでの変更を反映したもの）
- 実装方針
  - どのクラスに何を追加・変更するか
  - 新しく作る型・メソッドの名前（ゲーム側の言葉で命名する）
  - テストをどこにどう書くか（[`docs/TESTING.md`](../../docs/TESTING.md) に従う）
- コミットの分け方の予定（意味のある塊ごとに、何をどの順でコミットするか）
- 方針を決めるうえで迷った点と、推奨案およびその理由
- 手順1で未コミットの変更が見つかった場合は、その内容と、どう扱うか（コミットする・stashする・そのままにするなど）の確認

**この時点ではコードを編集しない。** ユーザーの回答を待つ。

## 3. 合意後、実装を進める

ユーザーが方針に合意したら（修正の指示があればそれを反映して）、以降はPR作成まで止まらずに進める。

### ブランチの準備

1. 未コミットの変更があった場合は、手順2で合意した扱い方に従って処理する。
2. `git checkout develop` → `git pull origin develop` でdevelopを最新にする。
3. [`.github/WORKFLOW.md`](../../.github/WORKFLOW.md) の命名規則に従って、developからブランチを切る（例: `feature/<英語のケバブケース>`）。typeはissueのラベル・テンプレートに合わせる。

### 実装とコミット

- 一度に大量の差分にならないよう、**意味のある塊ごとにコミットを分ける**。
  - 例: 「リファクタで下地を作る」「新しい型を作る（テスト込み）」「それを使って挙動を変える」「表示を変える」のように、各コミットが単独で読んで意味の通る単位にする。
  - リファクタと挙動変更は別のコミットにする。
  - 各コミットの時点でビルドとテストが通る状態を保つ。
- コミットメッセージは日本語で、そのコミットで何がどう変わるかを1行で書く（既存の `git log` の書き方に倣う）。
- テストは、対応するロジックを追加・変更したコミットに含める。数値埋めのテストは書かない。
- コミットのたびに `./gradlew check` が通ることを確認する。detektの指摘はコードの移動ですり抜けず、責務の切り出しなどで解消する。
- コミットしたらプッシュも続けて行う。

### 途中で確認したいことが出てきたら

**止まらずに、いったん自分の判断で最後まで進める。**

- 選択肢がある場合は、既存の設計・方針に最も沿う案を選んで進める。
- 何を判断したか・ほかにどんな案があったか・なぜその案を選んだかをメモしておき、最後の報告に含める。
- ただし、以下の場合は進めずにユーザーに確認する。
  - issueの要件そのものを満たせない、または要件が矛盾していると分かったとき
  - データの削除・外部への投稿など、取り消しにくい操作が必要になったとき

## 4. PRを作成する

- `gh pr create --base develop` でPRを作成する。
- タイトル・本文は [`.github/pull_request_template.md`](../../.github/pull_request_template.md) に従って書く。
- テンプレートに加えて、以下を守る。
  - Summaryでは、挙動の変更を先に書き、リファクタはその後に書く。
  - Summaryの中に、要検討点（手順5で報告するものと同じ内容）を簡潔に書く。

## 5. 対応内容を報告して待機する

PR作成まで終わったら、以下を画面に表示して、ユーザーの返答を待つ。

- 作成したPRのURL
- 対応内容: コミットごとに何をしたか（表にすると読みやすい）
- 要検討点: 実装中にユーザーへ確認したかったこと。それぞれについて
  - 何を判断したか
  - ほかにどんな案があったか
  - なぜ現在の実装を選んだか
- テスト: 何をテストしたか。テストを書かなかった部分があればその理由

PRのマージはユーザーがGitHubのUIから行う。マージを促したり、代わりに実行したりしない。
